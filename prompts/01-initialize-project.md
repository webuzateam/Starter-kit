# Управляемая инициализация проекта

## Общие правила

Во всех режимах охвати все 13 блоков из `docs/PROJECT_QUESTIONNAIRE.md`, но не обязательно задавай пользователю каждый вопрос. После первого зафиксированного блока установи статус `В ПРОЦЕССЕ`.

Для каждого значимого факта укажи один источник:

- `ПОДТВЕРЖДЕНО ПОЛЬЗОВАТЕЛЕМ`;
- `ВЫВЕДЕНО ИЗ ПРОЕКТА` — приложи путь или другое короткое основание;
- `ПРИНЯТО ПО УМОЛЧАНИЮ` — укажи безопасную рекомендацию Starter Kit;
- `ОТЛОЖЕНО`;
- `ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ПЕРЕД ДЕЙСТВИЕМ`.

Для каждого правила фиксируй статус `ПРИНЯТО`, `ИЗМЕНЕНО ПОЛЬЗОВАТЕЛЕМ`, `НЕ ПРИМЕНЯЕТСЯ`, `ОТЛОЖЕНО` или `ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ПЕРЕД ДЕЙСТВИЕМ`, а рядом — источник решения. Не называй вывод агента подтверждённым пользователем.

Противоречие, способное изменить текущий результат или безопасность, нужно разрешить до применения. Неизвестный низкорисковый факт можно отложить. Неизвестное разрешение на публикацию, deploy, внешнюю отправку, удаление, смену remote, переписывание истории или иное рискованное действие всегда означает запрет до явного подтверждения.

## Режим с сопровождением

Это рекомендуемый режим. Задавай вопросы блоками по 3–5 в формате коротких карточек. Для каждой карточки объясни, зачем нужен ответ, предложи 2–4 варианта, отметь рекомендацию и краткие последствия. Всегда разрешай `Не знаю / решить позже` и собственный вариант.

Для открытого вопроса сначала предложи 1–2 формулировки на основании разговора или файлов. Пользователь не должен писать всё с нуля, если агент может подготовить осмысленные варианты.

## Быстрый режим

Спроси только основные факты и отклонения от рекомендаций. Самостоятельно разнеси ответы и безопасные значения по всем 13 блокам, затем покажи единую сводку. Не скрывай отложенные решения и ограничения.

## Режим без брифа

1. Проведи read-only анализ структуры, README, конфигураций, исходников, документов и Git-состояния.
2. Выведи только те факты, для которых есть наблюдаемое основание.
3. Для обратимых внутренних настроек используй безопасные рекомендации Starter Kit.
4. Неизвестные сведения пометь `ОТЛОЖЕНО`, а разрешения на рискованные действия — `ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ПЕРЕД ДЕЙСТВИЕМ`.
5. Сформируй рабочее название и краткое описание проекта из доступного контекста; явно отметь их как вывод, если пользователь их не подтверждал.
6. Не задавай бриф. Задай вопрос только при противоречии, которое не позволяет создать безопасную конфигурацию.
7. Покажи итоговую сводку и объясни, какие действия останутся заблокированы.

## Перед применением

Когда все блоки охвачены выбранным режимом:

1. Установи статус `ОЖИДАЕТ ПРИМЕНЕНИЯ`.
2. Покажи выбранный режим и паспорт проекта с источниками данных.
3. Покажи принятые, изменённые и применённые по умолчанию правила.
4. Отдельно покажи отложенные решения и действия, требующие подтверждения.
5. Покажи языковую политику, Git-политику, реестр расширений, известные secret-пути, порог крупного файла, команды проверок и режим закрытия.
6. Предложи предварительный уровень готовности: безопасная внутренняя работа, работа с отложенными решениями или полная настройка.
7. Перечисли файлы, которые будут заполнены, включая замену корневого `README.md`.
8. Сообщи, что GitHub-репозиторий, публикация и deploy на этом этапе не выполняются.
9. Попроси отдельную команду `ПРИМЕНИТЬ`.

## После команды ПРИМЕНИТЬ

Команда действует после итоговой сводки любого режима. Она разрешает записать конфигурацию, но сама по себе не разрешает GitHub, публикацию, deploy или другие внешние действия. После неё:

1. Заполни `docs/PROJECT_CONTEXT.md` без выдуманных фактов и укажи происхождение неподтверждённых данных.
2. Полностью замени корневой `README.md` на README конкретного проекта. Он должен начинаться с зафиксированного рабочего названия и объяснять, что известно о проекте, для кого он, каковы его текущий этап, структура, запуск и проверки. Добавь ссылки на `docs/PROJECT_CONTEXT.md`, `docs/STATUS.md` и другие нужные документы. Неопределённые команды и факты не выдумывай; при необходимости прямо укажи, что они ещё не определены. Заголовок и введение мастер-шаблона `AI Project Starter Kit` в проектном README не сохраняй.
3. Сформируй `docs/PROJECT_POLICY.md` со статусом и источником каждого правила. Для отложенного рискованного решения запиши конкретное заблокированное действие.
4. Обнови `docs/STATUS.md`: режим START, уровень готовности, текущую работу, отложенные решения, заблокированные действия и следующий шаг.
5. Адаптируй проектные части `AGENTS.md`, не удаляя защитные правила.
6. Настрой `.gitignore` по подтверждённым или обнаруженным secret-путям. Не исключай предполагаемый путь без основания; при неизвестности заблокируй commit до проверки.
7. Обнови `.env.example` только именами переменных.
8. Заполни `docs/SECRETS.md` без значений.
9. Заполни `docs/INTEGRATIONS.md` обнаруженными или выбранными расширениями либо явно зафиксируй, что обязательные расширения пока не обнаружены.
10. Заполни `docs/GIT_POLICY.md`, `docs/BACKUP.md` и `docs/RECOVERY.md`.
11. Создай решение `docs/decisions/0001-правила-и-структура-проекта.md`. Статус `Принято` допустим только для явно подтверждённого выбора; выводы агента и безопасные временные значения фиксируй как предложения или действующие ограничения политики.
12. Установи статус опроса `ЗАВЕРШЕНА` и сохрани выбранный режим. Статус означает, что сводка применена, а не что все будущие решения уже известны.
13. Запусти аудит из `prompts/02-audit-project.md`.
14. Сформируй `docs/INITIALIZATION_REPORT.md`.

## Финальный отчёт

Отчёт должен показать проект, корень, режим START, количество данных по каждому источнику, принятые и изменённые правила, отложенные решения, заблокированные действия, результаты аудита, уровень готовности, Git-политику, расширения и их восстановление, режим секретов, крупные файлы, команду закрытия и следующий шаг.

Используй одну основную формулировку уровня готовности:

- `ГОТОВ К БЕЗОПАСНОЙ ВНУТРЕННЕЙ РАБОТЕ` — конфигурация применена, но для текущей работы ещё нужны уточнения или действуют строгие ограничения;
- `РАБОТАЕТ С ОТЛОЖЕННЫМИ РЕШЕНИЯМИ` — текущая работа определена, а будущие или рискованные действия имеют явные контрольные точки;
- `ПОЛНОСТЬЮ НАСТРОЕН` — критичных отложенных решений нет;
- `ПРОЕКТ НЕ ГОТОВ: ...` — команда `ПРИМЕНИТЬ` не завершена или существует противоречие, не позволяющее работать безопасно.
