# AI Project Starter Kit

Система запуска и ведения AI-проектов, которая хранит память проекта в файлах, а не только в истории чата. Starter kit помогает продолжить работу с другим AI-агентом или аккаунтом, восстановить текущее состояние и сохранить проект в приватном GitHub.

Сайт проекта: [презентация](https://webuza-ai-starter-kit.pages.dev/) и [полная пользовательская инструкция](https://webuza-ai-starter-kit.pages.dev/guide/).

## Самое короткое начало

1. Скопируйте содержимое этой папки непосредственно в корень нового проекта. Не создавайте дополнительную вложенную папку.
2. Откройте корень проекта в AI-агенте.
3. Отправьте отдельное сообщение `START`.
4. Выберите быстрый или полный опрос. В быстром режиме сообщите факты проекта и отклонения, а остальные рекомендуемые значения примите одной сводкой.
5. Проверьте итоговую сводку и отправьте `ПРИМЕНИТЬ`.
6. После отчёта «ПРОЕКТ ГОТОВ К РАБОТЕ» настройте Git и приватный GitHub через `prompts/03-setup-git-github.md`.
7. В конце содержательной работы отправляйте отдельную команду `закрываем сессию`.

## Зачем система устроена именно так

AI-чат удобен, но он не должен быть единственным местом, где хранятся цель, решения и состояние проекта. Чат может стать недоступен, переполниться или остаться в другом аккаунте. Поэтому важная информация раскладывается по понятным локальным файлам:

- правила работы живут в `AGENTS.md`;
- стабильное описание — в `docs/PROJECT_CONTEXT.md`;
- текущее состояние — в `docs/STATUS.md`;
- принятые правила — в `docs/PROJECT_POLICY.md`;
- причины важных решений — в `docs/decisions/`;
- история содержательных сессий — в `logs/sessions/`;
- фактическая история файлов — в Git.

Так новый агент сначала читает папку, восстанавливает картину и только потом меняет проект.

## Языки и будущая локализация

Название, структура и основные пути starter kit не привязаны к конкретному языку. Во время `START` пользователь выбирает основной язык проекта, дополнительные языки, правила перевода и язык технических материалов. До завершения настройки агент отвечает на языке текущего обращения пользователя.

Добавление нового языка не должно требовать переименования продукта или корневых файлов. Переводы пользовательских материалов хранятся раздельно и синхронизируются по правилам, подтверждённым во время опроса.

Сайт starter kit хранится как отдельный проект за пределами этой папки. Он не скрывается через `.gitignore` и не относится к содержимому данного репозитория. В Git проекта входят все значимые данные внутри его корня по правилам, выбранным во время `START`.

## Чистый шаблон и рабочий проект

Этот репозиторий — мастер-шаблон для публикации. Плейсхолдеры в `PROJECT_CONTEXT.md`, `STATUS.md` и других проектных документах намеренно не заполнены, а журналы разработки самого шаблона в `logs/sessions/` не создаются.

После копирования содержимого в новый проект команда `START` превращает эту же структуру в память конкретного проекта. Определить режим помогает `origin`: репозиторий `webuzateam/Starter-kit` остаётся чистым, а копия с другим или ещё не настроенным remote проходит обычную инициализацию.

## Как работает команда START

`START` срабатывает только как отдельная команда. Простое упоминание слова в тексте ничего не запускает.

Первый запуск проходит по состояниям:

```text
НЕ НАЧАТА → В ПРОЦЕССЕ → ОЖИДАЕТ ПРИМЕНЕНИЯ → ЗАВЕРШЕНА
```

Сначала агент делает короткий отчёт о составе starter kit и проверяет корневую папку без изменений. Затем предлагает быстрый или полный режим. Оба режима применяют все 13 блоков: паспорт и языки, границы, технологии и расширения, поведение AI, документацию, Git, секреты, крупные файлы, проверки, закрытие сессии, восстановление и отчёты. Быстрый режим сокращает число вопросов, но не пропускает правил.

После каждого завершённого блока подтверждённые ответы записываются в `docs/PROJECT_QUESTIONNAIRE.md`. Это позволяет продолжить опрос в новом чате. Перед применением агент показывает сводку. Команда `ПРИМЕНИТЬ` разрешает заполнить документы и провести аудит, но не разрешает молча создавать GitHub-репозиторий.

Если настройка уже завершена, повторный `START` ничего не перезаписывает: агент показывает цель, состояние и следующий шаг. Для изменения правил используется команда `ИЗМЕНИТЬ ПРАВИЛА ПРОЕКТА`.

## Что считается источником истины

При конфликте информации применяется такой порядок:

1. Текущее явное указание пользователя.
2. `AGENTS.md` и принятые правила из `docs/PROJECT_POLICY.md`.
3. `docs/STATUS.md` для текущего состояния.
4. `docs/PROJECT_CONTEXT.md` для стабильного описания.
5. Принятые решения из `docs/decisions/`.
6. Git для фактической истории файлов.
7. Session logs как вспомогательная история.
8. История чата как временный контекст.

## Git как резервная копия папки

По умолчанию Git сохраняет все значимые данные внутри корня проекта: исходники, документы, результаты и невоспроизводимые материалы. Секреты всегда исключаются. Системные метаданные вроде `.DS_Store` не являются памятью проекта. Политика для кэша, сборок и воспроизводимых зависимостей выбирается во время `START`, чтобы не раздувать репозиторий и не потерять важные файлы.

Git не хранит пустые каталоги, поэтому в рабочих зонах находятся поясняющие `README.md`. Служебная папка `.git` не добавляется как обычный файл, но её история передаётся удалённому репозиторию через push.

GitHub-репозиторий должен быть отдельным для каждого проекта и только приватным. Публичная видимость, force push, переписывание истории, удаление веток и смена согласованного `origin` не входят в обычное закрытие сессии.

## Как переносятся Skills, плагины и MCP

`docs/INTEGRATIONS.md` хранит единый реестр расширений, их источники, версии, область действия и проверку после восстановления. По умолчанию обязательных расширений нет, а лишние каталоги не создаются.

- Project Skills в `.agents/skills/` и их ресурсы могут храниться вместе с проектом.
- Исходники проектного плагина и project marketplace могут храниться в Git, но факт установки, кэш и OAuth-сессия не переносятся.
- Безопасная project MCP-конфигурация может храниться в `.codex/config.toml`; доверие к проекту, зависимости и авторизация восстанавливаются отдельно.
- Пользовательские Skills и глобальные MCP-настройки не входят в репозиторий: для них фиксируются источник, версия и инструкция повторной установки.

Токены и пароли расширений никогда не записываются в реестр. В проекте остаются только имена переменных окружения и безопасные проверки. После clone новый агент сначала читает реестр, затем восстанавливает выбранные компоненты и сообщает, что действительно работает.

## Секреты

Секреты не отправляются в GitHub. `.gitignore` исключает типовые `.env`, закрытые ключи и каталоги с credentials. Перед commit дополнительно проверяется содержимое подготовленных файлов, потому что токен может оказаться в обычном Markdown, JSON или исходнике.

`.gitignore` защищает по пути, а проверка секретов — по содержимому. Нужны оба механизма. В `docs/SECRETS.md` записываются только названия, расположение и способ восстановления. Значения токенов, паролей, seed phrases и мастер-паролей туда не помещаются.

## Крупные файлы

До commit агент проверяет размер новых и изменённых файлов. По умолчанию предупреждение начинается с 50 MiB. Если файл может не пройти ограничения GitHub, закрытие сессии приостанавливается до решения пользователя.

Агент показывает путь, размер, тип и варианты: обычный Git, Git LFS, сжатие, разделение, внешнее хранилище, исключение или отмена синхронизации. Ни один вариант не применяется автоматически.

## Обычный рабочий цикл

### Начало

Используйте `prompts/04-start-session.md`. Агент читает правила, контекст, статус, решения, последний подходящий лог и Git status. До получения задачи он ничего не меняет.

### Работа

Используйте `prompts/05-work-session.md` или сформулируйте задачу напрямую. Агент работает в границах задачи, запускает проверки и фиксирует только действительно важные решения.

### Закрытие

Отдельная команда `закрываем сессию` заранее разрешает без дополнительного согласования:

1. обновить `docs/STATUS.md`;
2. создать session log;
3. обновить решения и changelog только при необходимости;
4. выполнить проверки;
5. проверить секреты и размеры;
6. добавить все значимые изменения согласно принятой Git-политике;
7. создать содержательный commit;
8. выполнить обычный push в ранее согласованный приватный `origin`;
9. проверить результат и выдать отчёт.

Автоматизация останавливается при секрете, крупном файле, публичном remote, смене `origin`, конфликте, расходящейся истории, необходимости force push, потере авторизации или иной ситуации, требующей рискованного решения.

## Что попадает в отчёт закрытия

- исходная задача и результат;
- изменённые файлы и документы памяти;
- выполненные проверки и ошибки;
- результат проверки секретов;
- крупные файлы и принятое по ним решение;
- ветка, remote, commit и результат push;
- незавершённые вопросы;
- первый следующий шаг.

Если изменений нет, пустой commit не создаётся. В персональном backup-режиме неудачный тест не обязан блокировать сохранение состояния, но ошибка должна быть явно отмечена. Для командного или production-проекта это правило меняется во время опроса.

## Восстановление новым агентом

Дайте новому агенту `prompts/07-recovery.md`. Он должен восстановить цель, состояние, важные решения, риски, Git-состояние и следующий шаг до любых изменений. Успешный recovery drill — это способность нового агента за несколько минут объяснить проект только по локальным файлам.

## Важные границы

- Команда закрытия разрешает только документирование, безопасный commit и обычный push в заранее согласованный приватный remote.
- Она не разрешает deploy, публикацию, отправку материалов третьим лицам, удаление, force push или смену видимости.
- GitHub сохраняет только закоммиченные и отправленные файлы. Секреты из `.gitignore` должны восстанавливаться из отдельного защищённого хранилища.
- Инструкции starter kit полностью заполнены. Проектные поля намеренно заполняются ответами пользователя при `START`; агент не должен выдумывать их.

## Периодическая проверка

Запускайте `prompts/02-audit-project.md` после крупных изменений правил или структуры. Аудит проверяет цель, актуальность статуса, непротиворечивость политик, незаполненные поля, расширения, секреты, Git, крупные файлы и готовность к передаче новому агенту.
