# Опрос первого запуска

Статус настройки: **НЕ НАЧАТА**

Допустимые состояния: `НЕ НАЧАТА`, `В ПРОЦЕССЕ`, `ОЖИДАЕТ ПРИМЕНЕНИЯ`, `ЗАВЕРШЕНА`.

Этот файл одновременно является опросником и устойчивой записью подтверждённых ответов. Агент заполняет его блоками после команды `START`. Значения секретов сюда не записываются.

## Как проходить опрос

- Агент показывает краткую карту starter kit и проверяет корень без изменений.
- Вопросы задаются блоками по 3–5 за сообщение.
- Для необязательных настроек можно ответить `Принять рекомендуемые значения`.
- После блока агент кратко пересказывает ответы и записывает их сюда.
- Неясные и противоречивые ответы уточняются до применения.
- После полного опроса пользователь получает сводку и отправляет отдельную команду `ПРИМЕНИТЬ`.

## Блок 1. Паспорт проекта

1. Как называется проект?
2. Опишите проект одним абзацем.
3. Какую проблему он решает и какой конечный результат нужен?
4. Кто владелец, пользователь или аудитория?
5. Какой сейчас этап: идея, прототип, производство, эксплуатация или архив?

### Подтверждённые ответы

Заполняется при `START`.

## Блок 2. Языки и локализация

1. Какой язык является основным для интерфейса и пользовательских материалов?
2. Какие дополнительные языки понадобятся сейчас или в будущем?
3. На каком языке должны быть код, комментарии и техническая документация?
4. Нужно ли синхронно обновлять все переводы при изменении исходного текста?
5. Как хранить переводы: отдельными файлами, каталогами локалей или в системе управления контентом?

### Рекомендуемые значения

- До применения правил агент использует язык текущего обращения пользователя.
- Название продукта, репозитория и основные пути остаются нейтральными.
- Основной и дополнительные языки фиксируются в `PROJECT_CONTEXT.md`.
- Для каждого перевода указывается исходная версия и состояние актуальности.

### Подтверждённые ответы

Заполняется при `START`.

## Блок 3. Границы и структура

1. Что входит в проект?
2. Что явно не входит?
3. Является ли открытая папка корнем проекта?
4. Есть ли важные файлы за пределами корня?
5. Где должны находиться исходники, документы, данные и результаты?

### Рекомендуемые значения

- Файлы starter kit располагаются непосредственно в корне.
- Основная работа находится в `src/`, результаты — в `outputs/`.
- Внешние важные материалы описываются в `PROJECT_CONTEXT.md`; агент не копирует их без разрешения.

### Подтверждённые ответы

Заполняется при `START`.

## Блок 5. Источники истины

Подтвердите или измените:

1. `STATUS.md` — единственный актуальный снимок.
2. `PROJECT_CONTEXT.md` — стабильное описание.
3. `PROJECT_POLICY.md` и `AGENTS.md` — действующие правила.
4. `decisions/` — причины важных решений.
5. Git — фактическая история файлов, а chat — временный контекст.

## Блок 6. Поведение AI

1. Что агент может делать автономно внутри проекта?
2. Какие действия всегда требуют подтверждения?
3. Разрешена ли установка новых программ и зависимостей?
4. Разрешены ли внешние отправки, публикации и deploy?
5. Есть ли проектные запреты или чувствительные зоны?

### Рекомендуемые значения

- Чтение, анализ, редактирование по задаче и проверки внутри проекта разрешены.
- Удаление, публикация, deploy, отправка третьим лицам, смена remote и переписывание истории требуют отдельного разрешения.
- Команда `закрываем сессию` является заранее выданным разрешением только на документирование, commit и обычный push в согласованный приватный `origin`.

### Подтверждённые ответы

Заполняется при `START`.

## Блок 7. Документирование

1. Какой уровень session logs нужен: краткий, стандартный или расширенный?
2. Какие задачи считать содержательной сессией?
3. Нужно ли фиксировать безопасные названия выполненных команд?
4. Когда обновлять changelog?
5. Когда создавать отдельное решение?

### Рекомендуемые значения

- Стандартный лог: запрос, результат, файлы, проверки, решения, риски, следующий шаг.
- Changelog — только для пользовательских изменений.
- Решение — только для существенного выбора или риска.
- Полный чат и полный вывод терминала не копируются.

### Подтверждённые ответы

Заполняется при `START`.

## Блок 8. Git и GitHub

1. Используется новый или существующий репозиторий?
2. Кто владелец и как называется репозиторий?
3. Какой `origin` и какая основная ветка разрешены?
4. Подтверждается ли приватная видимость и правило «все файлы, кроме секретов»?
5. Нужно ли сохранять состояние при неудачных тестах?

### Рекомендуемые значения

- Один приватный GitHub-репозиторий на один проект.
- `main` для нового персонального проекта, `origin` как remote.
- Все неигнорируемые файлы сохраняются.
- В backup-режиме состояние сохраняется даже при ошибке теста, но ошибка явно фиксируется.

### Подтверждённые ответы

Заполняется при `START`.

## Блок 10. Крупные файлы

1. Есть ли базы, архивы, видео, модели или другие крупные бинарные файлы?
2. Какой порог предупреждения использовать?
3. Настроен ли Git LFS?
4. Допустимо ли внешнее хранилище для отдельных файлов?
5. Подтверждается ли обязательное решение пользователя до commit?

### Рекомендуемые значения

- Предупреждать от 50 MiB.
- Не включать Git LFS и не исключать файл автоматически.
- Показывать путь, размер, тип и варианты решения.

### Подтверждённые ответы

Заполняется при `START`.

## Блок 11. Закрытие сессии

Подтвердите, что отдельная команда `закрываем сессию` без дополнительного согласования разрешает:

- обновить память проекта;
- выполнить проверки;
- проверить секреты и размеры;
- добавить все неигнорируемые изменения;
- создать содержательный commit;
- выполнить обычный push в заранее согласованный приватный `origin`;
- выдать отчёт.

Она не разрешает deploy, публикацию, удаление, force push, смену remote или видимости.

### Подтверждённые ответы

Заполняется при `START`.

1. Какие материалы критичны для восстановления?

3. Какие проверки нужны после clone?
4. Нужно ли проводить периодический recovery drill?
5. Кто подтверждает продолжение работы после реконструкции?

### Рекомендуемые значения

- Новый агент сначала читает правила, политику, контекст, статус, решения и последний лог.
- Затем проверяет Git и даёт отчёт до изменений.
- Recovery drill проводится после крупных изменений структуры.

### Подтверждённые ответы

Заполняется при `START`.
