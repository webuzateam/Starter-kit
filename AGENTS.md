# Канонические инструкции проекта для AI-агентов

Этот файл является главным набором постоянных правил для AI, работающего в проекте. Пользовательские инструкции имеют приоритет. При неоднозначном или рискованном конфликте сначала объясни его и запроси решение.

Версия протокола первого запуска: **START v2**. Каноническая схема содержит ровно три режима: **с сопровождением**, **быстрый** и **без брифа**. Другие списки режимов в этой версии Starter Kit не используются.

## Команды управления

- Отдельное сообщение `START` при незавершённой настройке запускает `prompts/00-start.md`.
- `START` после завершённой настройки показывает краткий статус и не перезаписывает документы.
- При первом `START` пользователь выбирает режим **с сопровождением**, **быстрый** или **без брифа**.
- Отдельная команда `ПРИМЕНИТЬ` действует после итоговой сводки любого режима и запускает этап применения из `prompts/01-initialize-project.md`.
- Отдельная команда `ИЗМЕНИТЬ ПРАВИЛА ПРОЕКТА` запускает повторную настройку с выбором режима без автоматического удаления прежних решений.
- Отдельная команда `закрываем сессию` запускает `prompts/06-close-session.md` и считается явным разрешением на безопасный commit и обычный push в заранее согласованный приватный `origin`.
- Упоминание этих фраз внутри обычного текста не является командой.

## Перед любой работой

Прочитай в таком порядке:

1. `AGENTS.md`.
2. `docs/PROJECT_POLICY.md`.
3. `docs/PROJECT_CONTEXT.md`.
4. `docs/INTEGRATIONS.md`, если задача затрагивает инструменты или восстановление.
5. `docs/STATUS.md`.
6. Актуальные принятые решения в `docs/decisions/`.
7. Последний подходящий файл в `logs/sessions/`, если он нужен для текущей задачи.
8. Проверь Git status, если Git инициализирован.

Если команда `ПРИМЕНИТЬ` ещё не выполнена, не начинай обычную проектную работу и предложи `START`. После применения адаптивной настройки разрешена безопасная внутренняя работа; отложенное решение блокирует только связанное с ним действие.

## Источники истины

- Текущая работа и следующий шаг: `docs/STATUS.md`.
- Стабильная цель и границы: `docs/PROJECT_CONTEXT.md`.
- `README.md` — человекочитаемое введение именно в текущий проект; после инициализации он не должен оставаться инструкцией Starter Kit.
- Действующие правила: этот файл и `docs/PROJECT_POLICY.md`.
- Причины существенных решений: `docs/decisions/`.
- Фактическая история файлов: Git.
- Session logs являются историей, а не текущим состоянием.
- Не полагайся на чат как на единственную память.

## Рабочие правила

- Работай только в корне открытого проекта и его дочерних каталогах.
- Не создавай дополнительную папку с именем проекта внутри уже открытого корня.
- Соблюдай границы текущей задачи и сохраняй пользовательские изменения.
- Для чтения, обзора и обсуждения не изменяй проект без явного запроса, кроме фиксации данных выбранного режима в `PROJECT_QUESTIONNAIRE.md` во время `START`.
- Не удаляй, не перезаписывай историю, не публикуй, не деплой и не отправляй данные третьим лицам без явного разрешения.
- Не показывай и не записывай значения секретов.
- Не выдавай вывод из файлов или безопасное значение по умолчанию за подтверждённый пользователем факт. В контексте и опроснике указывай источник значимых данных.
- Вопросы настройки задавай как короткие карточки: объясни, зачем нужен ответ, предложи 2–4 подходящих варианта, отметь рекомендацию и разреши ответы `Не знаю`, `Решить позже` и собственный вариант.
- В режиме без брифа самостоятельно принимай только безопасные и обратимые настройки. Публикация, deploy, внешняя отправка, удаление, смена remote, переписывание истории и иные рискованные действия остаются заблокированы до явного разрешения.
- Не копируй полный вывод терминала в session log. Сохраняй только полезный итог и безопасные названия команд.
- Запускай релевантные проверки. Если проверка пропущена, укажи причину.
- До применения настроек отвечай на языке текущего обращения пользователя.
- После инициализации соблюдай основной и дополнительные языки, записанные в контексте и политике проекта.
- Не добавляй языковой суффикс в название продукта, репозитория или основные пути, если пользователь явно не выбрал такую схему.

## Режим мастер-шаблона

Если пользователь явно разрабатывает сам Starter Kit или согласованный `origin` указывает на `webuzateam/Starter-kit`, считай открытую папку чистым мастер-шаблоном:

- не заполняй шаблонные `PROJECT_CONTEXT.md`, `PROJECT_QUESTIONNAIRE.md`, `PROJECT_POLICY.md`, `STATUS.md` и `INITIALIZATION_REPORT.md` данными разработки шаблона;
- не создавай session logs о сопровождении шаблона;
- изменяй только распространяемые файлы продукта в пределах явной задачи;
- при команде `закрываем сессию` проверяй, фиксируй и отправляй только реальные изменения продукта без загрязнения плейсхолдеров.

В скопированном пользовательском проекте с другим или ещё не настроенным `origin` команда `START` заполняет документы подтверждёнными данными, выводами из файлов, безопасными значениями по умолчанию и явно отмеченными отложенными решениями — в зависимости от выбранного режима.
В этом режиме этап `ПРИМЕНИТЬ` также обязательно заменяет корневой `README.md` на описание конкретного проекта до настройки Git.

## Skills, плагины и MCP

- Реестр и способ восстановления расширений хранятся в `docs/INTEGRATIONS.md`.
- Project Skills и безопасная проектная конфигурация сохраняются в Git, если выбраны пользователем.
- Установленное состояние, кэш, пользовательские/глобальные настройки и авторизация не считаются перенесёнными через Git.
- Не записывай credentials в файлы расширений; фиксируй только имена переменных и безопасную инструкцию восстановления.
- Не создавай необязательные каталоги расширений заранее.

## Документирование

- `docs/STATUS.md` обновляется при завершении содержательной сессии.
- Session log создаётся в формате `YYYY-MM-DD-HHMM-краткая-тема.md`.
- `docs/CHANGELOG.md` обновляется только при значимом для пользователя изменении.
- Новое решение создаётся только при существенном выборе архитектуры, инструмента, структуры, риска или политики.
- Не создавай `logs/actions.md` и не дублируй один и тот же отчёт во всех документах.

## Git и GitHub

- По умолчанию сохраняй все значимые данные проекта, кроме путей, явно исключённых как секретные.
- Политику для системного мусора, кэша и воспроизводимых зависимостей подтверждай во время `START`; не исключай содержательные материалы автоматически.
- Перед commit проверяй staged-состав, содержимое на секреты и размеры новых/изменённых файлов.
- Предупреждай о файлах от 50 MiB или от порога, установленного в политике проекта.
- Решение о Git LFS, сжатии, внешнем хранилище или исключении принимает пользователь.
- GitHub-репозиторий должен быть приватным.
- Не используй force push, не переписывай историю и не меняй `origin` автоматически.
- Не создавай пустой commit.
- Если tests не прошли, следуй режиму из `docs/PROJECT_POLICY.md`; в персональном backup-режиме сохрани состояние и явно отметь ошибку.

## Автоматическое закрытие

После отдельной команды `закрываем сессию` не спрашивай дополнительного подтверждения для документирования, commit и обычного push, если одновременно выполнены условия:

- `origin` заранее согласован;
- репозиторий приватный;
- нет подозрения на секрет;
- нет нерешённого крупного файла;
- не требуется force push, удаление, rebase с риском или смена remote;
- авторизация действительна.

Если условие нарушено, остановись безопасно и выдай отчёт о препятствии.

## Финальный отчёт задачи

Сообщи:

1. Что сделано.
2. Какие файлы изменены.
3. Какие проверки выполнены.
4. Какие риски или ограничения остались.
5. Какой следующий шаг.
